What is GeckoRegen?

GeckoRegen is a self-healing regulatory compliance monitor. Compliance teams must track regulatory changes across many jurisdictions and websites. When a regulator redesigns their site, scrapers break silently — critical updates get missed, potentially costing millions in fines.

GeckoRegen detects breakage automatically, heals the scraper via Bright Data's Self-Healing API, validates the fix against data-quality constraints, and builds persistent memory that learns from every change.

Monitor → Detect → Heal → Validate → Memory

How to Read the Health Grid

Each regulator is a card. The card color reflects the scraper's latest health status:

Green — Healthy All fields populated, schema checks pass. Scraper working normally.
Yellow — Degraded Some optional fields missing or population rate below threshold. Still returning data but needs attention.
Red — Broken Required fields returning null, zero records, or critical schema failure. Self-healing triggered.

Cards animate when status changes: red pulse on break, green pulse on heal.

What Happens When a Scraper Breaks

  1. Detection — The monitor runs the scraper via Bright Data's Trigger/Dataset API. The detector diffs the result against the expected schema (field types, regex patterns, population rate).
  2. Classification — Failures are classified by severity: critical for required fields, warning for optional fields, info for minor drift.
  3. Health update — The regulator card turns red in the dashboard (live via SSE). The health grid pulses.
  4. Heal triggered — A contextual prompt is generated with: the broken field name, expected pattern, and last-known-good value. This is sent to BD's Self-Healing API (refactor_template).

How Self-Healing Works

  1. Contextual prompt — Not generic "it broke." The prompt names the field, shows the expected regex, includes a real example value from the last-known-good snapshot.
  2. BD Self-Healing API — Submits the prompt, polls for completion, auto-approves if BD waits for human-in-the-loop.
  3. Validation gate — The healed scraper is re-run on the same URL. The output is checked: population rate ≥ 90%, format consistency, type match, record count > 0. This is the differentiator — we don't trust BD blindly.
  4. Retry with sharper prompts — If validation fails, the prompt is sharpened with the specific failure reason. Max 3 attempts.
  5. Memory update — Every heal event is logged: broken fields, prompt used, attempts, validation result, duration. Regulator profiles learn success rates over time.

Step-by-Step Demo for Judges

1
Open the dashboard

You're looking at the health grid. All regulators should show green (healthy) if the monitor has run. If the grid is empty, click Simulate Break to trigger the first scan.

2
Click "Simulate Break"

This POSTs to /api/scan, triggering a scan. The scraper runs against the sandbox site. If the sandbox has been modified (simulating a site redesign), the scraper will return broken fields — watch the card turn red with a pulse animation.

3
Watch the self-healing

The healer generates a contextual prompt and sends it to BD's Self-Healing API. The healing timeline (bottom right) shows the event appearing. When the fix validates, the card pulses green and returns to healthy.

4
Check the change feed

The left panel shows recently detected regulatory changes with severity badges. Each entry links to the original article.

5
Watch the live event stream

The bottom panel shows SSE events arriving in real time: scan_started, health_changed, heal_triggered, heal_completed. This is the live nervous system of the monitor.

6
Or click "Run Demo" above

This triggers the full automated demo sequence — scan, detect break, heal, validate — so you can watch the entire pipeline flow without manual clicks.

Architecture at a Glance

  • Bright Data Scraper Studio — builds and runs scrapers per regulator site
  • Self-Healing API — regenerates broken scraper code with contextual prompts
  • Trigger/Dataset API — runs scrapers programmatically and downloads results
  • SQLite — persistent memory: regulators, health scores, changes, heal events, profiles
  • Flask + SSE — live dashboard with real-time status updates
  • Vanilla JS frontend — no build step, no frameworks, no node_modules
